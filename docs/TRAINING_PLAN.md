# 股票消息公司识别系统：训练与上线规划

最后更新：2026-08-21

## 1. 最终目标

输入一条中文或英文消息，识别消息实际提到的一家或多家公司，并输出受控主数据中的标准股票代码。

系统不允许模型自由生成股票代码。公司的交易所、股票代码和平台合约映射始终由 SQLite 主数据提供。

目标市场：

- 美股
- A股
- 港股
- 以币安 Futures 当前上线标的为优先范围

## 2. 当前进度

截至 2026-08-21，项目已经完成：

- WebSocket 实时消息采集
- Twitter 与新闻网站两种消息格式标准化
- SQLite 持久化、去重和增量读取
- 上游 `stocks` / `stoks` 正则候选保存
- 本地规则识别与多公司输出
- 浏览器标注页面
- 币安 TradFi 合约同步与资产分类
- SQLite 公司主数据与 `companies.csv` 人工规则合并

当前数据基线：

| --- | ---: |
| 有效消息 | 5,599 |
| 已标注消息 | 5,526 |
| 未标注消息 | 73 |

运行时额外保留了原公司库中的埃克森美孚、万豪国际和花旗集团，因此运行时公司总数比币安目标公司多3家。

这些数量足以开始第一次基线实验，但不能只根据总量判断能否上线。正式训练前还必须检查公司覆盖率、候选召回率、重复消息和标签质量。

## 3. 系统最终结构

```text
WS消息
  ↓
文本标准化与去重
  ↓
规则、别名、股票代码、stocks/stoks 召回候选公司
  ↓
经典ML快速判别（TF-IDF + LogisticRegression）
  ↓
疑难候选语义判别（可选 reranker）
  ↓
阈值过滤，保留0到多家公司
  ↓
SQLite映射标准股票代码
```

职责划分：

- 规则系统负责尽可能找全候选，追求高召回率。
- 经典ML模型负责快速过滤大部分正则误报，建立低成本基线。
- reranker负责处理经典ML无法稳定判断的疑难候选；是否启用由离线实验决定。
- SQLite负责输出合法、稳定、可维护的标准代码。

## 4. 要训练的任务

训练任务定义为“消息—候选公司文本对二分类”，而不是121分类，也不是股票代码生成。

输入示例：

```json
{
  "message": "We need to act now before it is too late.",
  "candidate": "ServiceNow | NYSE:NOW | aliases: ServiceNow",
  "label": 0
}
```

正样本示例：

```json
{
  "message": "ServiceNow announced stronger quarterly revenue.",
  "candidate": "ServiceNow | NYSE:NOW | aliases: ServiceNow",
  "label": 1
}
```

一条多公司消息会拆成多个文本对，各自独立判断。这样既支持 `no_match`，也支持一条消息返回多家公司。

不采用直接多分类的原因：

- 一条消息可能包含多家公司。
- 一条消息可能不包含任何目标公司。
- 新增公司会改变分类类别，导致频繁重训。
- 热门公司样本会压制样本较少的公司。
- 生成式模型可能输出不存在的代码。

## 5. 模型实验顺序

第一版先训练经典ML基线：

```text
字符级与词级 TF-IDF + LogisticRegression
```

原因：

- 当前独立正样本消息只有419条，经典ML更适合先建立可靠基线。
- 训练和迭代速度快，CPU部署简单，便于检查特征与错误案例。
- 字符 n-gram 对中英文、股票代码、大小写和短别名都比较有效。
- 可以与人工构造的通用匹配特征组合。

可选的第二个经典ML实验：

```text
LightGBM + TF-IDF降维特征或结构化匹配特征
```

LightGBM主要用于判断结构化特征能否改善长尾公司和碰撞别名，不作为第一项必须实现的模型。

在微调之前，先运行未微调的语义基线：

```text
BAAI/bge-reranker-base
```

它原生适合“文本A与文本B是否相关”的 Cross-Encoder 任务，并支持中文和英文。先做零样本测试，可以判断语义模型相对经典ML的提升是否足以覆盖其训练和部署成本。

只有在冻结测试集上证明有价值后，才微调 reranker。后续备选：

- `BAAI/bge-reranker-v2-m3`：多语言能力更强，但模型更大。
- `microsoft/mdeberta-v3-base`：使用序列分类头完成文本对二分类。

第一阶段不训练大语言模型，不训练从消息直接生成代码的模型。

## 6. 训练数据生成规则

每条已标注消息先构建候选集合：

1. 本地名称、别名、品牌和股票代码规则命中的公司。
2. 上游 `stocks` / `stoks` 给出的候选公司。
3. 人工标注为正确、但前两种方法没有召回的公司。
4. 少量随机无关公司，用作普通负样本。

标签生成：

- 候选代码在人工 `correct_codes` 中：`label=1`。
- 候选被规则或上游召回，但不在 `correct_codes` 中：困难负样本，`label=0`。
- 随机抽取的无关公司：普通负样本，`label=0`。

负样本策略：

- 优先保留规则误报和上游正则误报，这些样本最有训练价值。
- 每个正样本搭配约3到10个负样本，具体数量由数据审计决定。
- 不为每条消息机械生成全部121家公司，否则类别会严重失衡。
- 没有目标公司的消息也要保留其困难负样本。

经典ML除TF-IDF外，可加入以下通用二元或数值特征：

- 是否精确命中公司全称、别名或股票代码。
- 股票代码前是否带 `$`，是否为独立单词，是否全大写。
- 命中位置位于标题、正文、用户名、转发人还是 `@mention`。
- 候选附近是否出现 `stock`、`share`、`company`、`earnings`、`股票`、`公司`、`财报` 等上下文词。
- 上游 `stocks` / `stoks` 是否给出相同候选。
- 别名长度、歧义等级、单条消息候选数量和命中次数。
- 消息来源是新闻还是Twitter。

`NOW`、`BE`、`Strategy`、`Oracle`、`Coherent`、`Windows`、`NOK`、`BOT` 等已知碰撞案例用于构建困难负样本和验证集。尽量使用可迁移的通用特征，不让模型只记住少数公司的硬编码规则。

计划中的训练记录字段：

```text
message_id
source_id
source_type
message_text
candidate_code
candidate_profile
label
negative_type
annotation_confidence
split
```

## 7. 数据清洗与切分

正式训练前必须完成：

- 清理空文本和异常文本。
- 检查中文是否存在乱码或替代字符。
- 合并相同新闻、转推和正文近似重复消息。
- 检查人工标签是否包含已经停用或不存在的代码。
- 统计每家公司正样本数量。
- 统计中文、英文、Twitter、新闻网站的样本分布。
- 统计规则候选和上游候选的召回率。

数据集建议切分：

- 训练集：70%
- 验证集：15%
- 测试集：15%

切分约束：

- 以原始消息为最小切分单位；同一消息生成的全部候选 pair 必须位于同一集合。
- 相同 `source_id` 必须位于同一集合。
- 重复或近似重复消息必须位于同一集合。
- 优先按时间切分，使用较新的消息作为测试集。
- 测试集在调参期间保持冻结。

即使候选 pair 最终扩增到数千条，它们仍主要来自419条正样本消息，不能当作数千条独立语义样本。禁止随机拆分同一消息产生的 pair 或重复新闻，否则会产生数据泄漏，使测试结果虚高。

## 8. 训练参数起点

经典ML第一轮：

```text
word TF-IDF: 1-2 gram
char TF-IDF: 2-5 gram
classifier: LogisticRegression
class_weight: balanced 与不加权都测试
threshold: 仅使用验证集搜索
```

特征消融实验至少比较：

1. 只使用TF-IDF。
2. TF-IDF加通用结构化特征。
3. 可选LightGBM结构化特征模型。

reranker微调仅在零样本基线有价值时进行，第一轮参数暂定：

```text
max_length: 256
loss: Binary Cross Entropy
epochs: 2-4
learning_rate: 1e-5 到 3e-5
batch_size: 视显存选择8或16
early_stopping: 根据验证集F1或Precision停止
```

这些只是起点，最终参数必须由验证集结果决定。类别不平衡时优先使用困难负样本采样或正样本权重，不能用测试集调参。

## 9. 必须评估的指标

候选召回阶段：

- Candidate Recall：真实公司是否出现在候选集合中。

模型判别阶段：

- Precision
- Recall
- F1
- 正样本与负样本混淆矩阵
- 各公司、各语言、各来源的分组指标

整条消息阶段：

- 公司集合完全正确率
- 多公司消息完全正确率
- `no_match` 误报率
- 漏掉任意一家公司的比例

性能指标：

- 端到端 p50、p95 和 p99 延迟。
- 端到端范围包括候选召回、文本预处理、批量模型推理和SQLite代码映射。
- 分别记录单候选与多候选消息，并使用与生产环境一致的CPU或GPU测试。

第一版目标值：

| 指标 | 初始目标 |
| --- | ---: |
| Candidate Recall | ≥ 99% |
| 公司判断 Precision | ≥ 98% |
| 公司判断 Recall | ≥ 95% |
| `no_match` 误报率 | ≤ 1% |

这些是上线目标，不是保证值。第一轮训练主要用于建立真实基线，之后再根据错误类型调整。

## 10. 上线策略

模型不能训练完成后直接替换现有规则系统，应分阶段上线：

### 阶段A：离线评估

- 在同一冻结测试集上运行规则系统、经典ML和reranker。
- 至少对比规则单独运行、规则加LogisticRegression、未微调reranker和微调reranker。
- 测量完整链路的端到端 p95 延迟，而不是只测单个候选的平均 forward pass。
- 输出错误案例报告。

### 阶段B：影子运行

- WS正常使用原结果。
- 新模型同步计算，但不影响正式输出。
- 保存模型分数和差异，持续人工复核。

### 阶段C：低风险启用

- 只对高置信度结果启用模型。
- 模型与规则冲突时优先进入复核队列。
- 保留快速关闭模型的配置开关。

### 阶段D：正式运行

- 监控误报率、漏报率、延迟和新公司覆盖率。
- 保存线上错误样本，进入下一轮增量训练。

## 11. 新增公司时是否重训

新增公司的一般流程：

1. 写入 SQLite 公司与证券主数据。
2. 添加公司全称、简称和可靠别名。
3. 规则系统能够召回该公司。
4. 语义模型使用消息与新公司资料进行判断。

通常不需要为了每一家新公司立即重新训练。只有当新公司产生较多歧义、误报或漏报时，才把新样本加入下一次周期训练。

## 14. 下一步

下一项开发任务不是立即启动训练，而是实现：

```text
数据审计脚本 + 训练数据导出脚本
```

完成后应先回答以下问题：

- 118家目标公司中有多少家公司至少出现过一次正样本？
- 各公司的正样本是否过度不均衡？
- 规则与上游候选的合并召回率是多少？
- 最容易误报的代码和别名有哪些？
- 去重后实际可用于训练的正负文本对有多少？

这些问题有明确答案后，再正式下载模型并开始第一次训练实验。
