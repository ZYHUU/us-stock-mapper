# 2026-08-24: 冻结测试集切分泄漏修复 + 两轮隐私检查修复（v0.1.0 发布）

## 背景

标注积压清空后（正样本消息从约1484条涨到2162条），用新数据快照重新训练 `classic-lr` 系列，
并按项目约定把测试集永久冻结成同一批消息 id，新旧模型在同一份测试集上比较。这个过程中
先后发现并修复了三个独立问题，最终发布的是第三轮修复后的 `classic-lr-v6`。

## 问题一：train/val/test 近重复内容泄漏

第一版按时间重新切分测试集时，扫描发现测试集和训练/验证集之间存在真实的近重复内容跨集合
泄漏：同一条转发/复制粘贴文案（比如一条新闻表态的转发、一条营销文案的复读）换了个消息 id，
一份落在训练集、另一份落在测试集。原因是原来的去重逻辑只按逐字节完全相同的文本分组，
漏掉了"内容相同、URL 或措辞有细微差异"的近重复。

**怎么修的**：`find_duplicate_clusters()` 用归一化文本 + 稀有词倒排索引找候选近重复对，
`SequenceMatcher` 相似度达标且两条消息的真实候选公司代码集合兼容（避免把"同一个推文模板、
不同标的公司"的消息错误合并，比如"鲸鱼预警：\$MSFT 期权成交" vs "\$AAPL 期权成交"）才聚类，
聚类后整体分进同一个 split。修复后重新扫描确认没有残留的跨集合真实泄漏，也没有误伤合法的
不同样本。第一版带泄漏的指标已作废，不采纳。

## 问题二：词表包含近乎完整句子的原文片段（第一轮隐私检查发现）

修好切分泄漏、训出 `classic-lr-v4` 后，在打包公开发布前的隐私检查环节，扫描 `model.joblib` 里
`word_vectorizer` 的词表，发现里面混进了长度超过 30 个字符、接近完整句子的中文原文片段。

根因：scikit-learn `TfidfVectorizer` 默认的 `token_pattern`（`r"(?u)\b\w\w+\b"`）不切分中文——
一整段没有空格的中文会被当成一个"词"整体吃掉。这既是隐私/版权问题（第三方抓取内容的原文片段
字面出现在要公开发布的模型文件里），也是特征质量问题（整句当一个 token 几乎没有跨消息的
泛化能力，本质上是死记硬背）。

**怎么修的**：把 `word_vectorizer` 的 `token_pattern` 限制成只匹配 ASCII 单词或单个中文字符
（`WORD_TOKEN_PATTERN = r"[A-Za-z0-9]+|[一-鿿]"`），中文的泛化信号完全交给不受此问题影响的
字符 n-gram（`char_vectorizer`，2-5 字符窗口）承担。用同一份数据快照重新训练成 `classic-lr-v5`，
测试集指标跟修复前的 v4 基本持平甚至略好，说明那些整句 token 本来就是过拟合噪声，不是有用信号。
`classic-lr-v4` 本身从未发布过。

**`classic-lr-v5` 当时看起来已经可以发布了**（测试集 Precision 0.938），但在真正上传发布物之前
又做了一轮更彻底的复查。

## 问题三：词表仍残留真实用户名（第二轮隐私检查发现，更彻底）

第二轮复查明确要求不接受"训练数据来自公开社交媒体、所以词表里出现公开用户名可以接受"这个
理由，重新扫描词表，确认找到了真实存在、可识别到具体个人的 Twitter 用户名片段——比如一条
群体艾特消息（`@Kashifabbasiary @JavedChaudhry ...`）里的两个真实用户名，作为 bigram 原封不动
出现在词表里。这不是问题二那种"整句"级别的泄漏，而是词袋模型的结构性特征：任何在真实文本上
训练的 TF-IDF 模型，只要一个词/词组在训练集里出现过 `min_df` 次以上就会进词表——**不脱敏原始
文本，这个问题没法只靠调参数或者加免责声明解决**。

**怎么修的**：新增 `src/text_sanitize.py`（`sanitize_message_text()`），在文本进入 TF-IDF 向量化
和结构化特征提取**之前**统一脱敏：

- URL、邮箱、长度≥6位的数字ID（比如区块号、追踪ID）替换成占位符 `[URL]` / `[EMAIL]` / `[ID]`
- `@handle` 默认替换成通用占位符 `[HANDLE]`；只有当 handle 精确匹配（不是子串包含）公司注册的
  ticker/别名/品牌名时，才替换成公司名（保留真正有用的信号，比如提到官方账号）
- 股票 cashtag（`$NVDA`）、已注册的纯数字股票代码（比如 A 股 `688825`）不受影响，原样保留——
  这些是分类任务真正需要的信号，不是需要脱敏的个人信息

**这一步训练和线上推理必须共用同一个函数**（避免重演更早之前踩过的
`candidates_in_message` train/serve 特征偏差坑）：`build_training_dataset.py` 在把训练特征
落盘成 `candidate_pairs.jsonl` 时调用；`semantic_matcher.py` 的 `SemanticMatcher.score()`
在真实推理路径里对同一条消息调用同一个函数。规则层的候选召回（`mapper.identify()`）用的
仍然是脱敏前的原文，脱敏只影响分类器看到的特征文本，不影响候选生成。

这个修复顺带解决了一个已知的误判类别：`@Tesla_Teslaway` 这类"handle 里包含公司名但不是官方
账号"的粉丝账号，之前模型可能靠死记硬背这个具体字符串学会拒绝它；脱敏后这个具体字符串不再
进入特征，但因为白名单是精确匹配、`Tesla_Teslaway` 跟 `Tesla` 不精确相等，脱敏后这类 handle
被替换成通用 `[HANDLE]` 占位符——泄漏问题解决了，误判缓解的副作用也保留了下来。

用同一份数据快照重新训练成 `classic-lr-v6`。词表复查确认：整句中文泄漏、URL、邮箱、已知真实
用户名全部为 0；保留下来的长数字串只有真实股票代码，`@X` 这类平台品牌名因为单字符 handle 不做
脱敏也正常保留（这是预期行为，不是遗漏）。

## 结果

| 模型 | 阈值 | Precision | Recall | F1 |
| --- | ---: | ---: | ---: | ---: |
| classic-lr-v3（上一个发布版本） | 0.6555 | 0.868 | 0.982 | 0.921 |
| classic-lr-v5（未发布，词表仍有用户名残留） | 0.6804 | 0.938 | 0.968 | 0.953 |
| **classic-lr-v6（本次发布，v0.1.0）** | 0.6396 | **0.907** | 0.975 | **0.940** |
| 规则基线 | — | — | — | 0.424 |

（classic-lr-v3 的数字是在这次修复泄漏后的同一份测试集上重新打分得到的，不是引用旧报告的数字，
保证是真正的同集合对比。）

**如实说明代价**：脱敏让 Precision 从 v5 的 0.938 掉到 v6 的 0.907——这不是训练波动，是隐私修复
的真实代价：模型原来部分依赖对特定 handle 字符串的死记硬背来判断，脱敏之后这部分信号被移除了。
即便如此，v6 相对上一个真正发布过的版本 v3 仍然是明确提升（Precision +3.9pt，F1 +1.9pt）。

## 结论 / 后续

- Precision 0.907 相对 v3 的 0.868 是明确提升，但仍未到项目自定的 98% 长期目标——这次发布把
  98% 当作持续优化方向，不当作 v0.1.0 的硬门槛。
- 影子模型 `lightgbm-shadow-v3`（同一批数据训出，脱敏修复*之前*训的）相对 `lightgbm-shadow-v2`
  是权衡而非净提升（Recall 到满分但 Precision 下降，F1 基本打平），决定不转正，继续用 v2 跑
  影子观察；不打算单独为它重跑脱敏修复，因为它本来就不对外发布，只在私有工作区跑影子对照。
- 后续用新产生、人工复核的生产数据继续积累修正样本，下一次训练前先看是否需要扩大标注量，
  阈值调整只能在验证集上做，测试集的比较基准维持不变（同一批冻结的消息 id）。
